The research is done, and the main finding changes the plan. In this UCX build (1.24.0, aarch64, glibc 2.43), UCM never replaces malloc. Vanilla UCX should work under malloc-tracer with three tracer changes and no UCX patches. A scratch experiment with those changes passed the xpmem rcache test 3 out of 3 times in both libc and NextHeap modes. The full write-up is in 2026-10-13-ucx-ucm-integration-design.md. Nothing is implemented or committed.

What UCM does to the address space

  • UCM's default mode (bistro) overwrites the start of eight libc functions (mmap, munmap, mremap, madvise, brk, sbrk, shmat, shmdt) with a jump to its own code. This happens inside libucs's constructor and adds about 0.4 s to startup.
  • Every unmap in the process then fires a VM_UNMAPPED event before the pages go away, including glibc malloc's own internal unmaps.
  • UCM's malloc self-test passes on those hooks alone, so its bundled ptmalloc is never installed. The debug log shows "malloc/free hooks were not called".
  • The other mode, reloc, does swap in ptmalloc, but it hangs vanilla UCX on this machine even without the tracer. I'm treating it as out of scope.

Who registers callbacks with UCM

  • Only the UCP registration cache (rcache) uses VM_UNMAPPED. Its callback queues the range, and the next lookup in the cache invalidates and re-registers it.
  • The remaining consumers use GPU alloc/free events, which don't depend on malloc: the memory-type cache and the gdr_copy and rocm_copy caches.
  • Open MPI reaches the same callbacks by its own route: it tells UCM that unmap events are reported externally and forwards its own munmap hooks to ucm_vm_munmap(). MPICH relies on UCM's hooks directly.

What broke under the tracer, and the fixes

  1. Startup crash. libucs's constructor runs before ours. Our malloc returns NULL while unresolved, so strdup crashes (confirmed in gdb). Fix: run our initialization once from the null check the hooks already have, plus sbrk(0) so UCM's startup self-test passes on the first try.
  2. NextHeap deadlock. UCX's logger holds a lock and calls strdup. NextHeap's first-allocation setup then trims a mapping with libc munmap, which fires UCM's callback, which tries to log and spins on the same lock. Fix: mappings the application never sees use raw syscalls, so malloc never runs UCX code.
  3. Freeing application memory must stay visible to UCM. It must go through libc munmap. I checked both directions: freeing a 1 MiB block produced the event covering the whole block. Routing that same release through a raw syscall dropped the event and left a stale cache entry.

Decisions for you

  • Bootstrap approach. I recommend full initialization from the first hook call. The earlier review's alternative passes early calls straight to glibc, but then UCX's constructor-time allocations go untraced. Either way, AGENTS.md needs an exception to "no fallback initialization in hooks".
  • New rule in AGENTS.md: raw syscalls for allocator-private mappings, libc munmap for releasing application memory.
  • Loader defaults. Set UCX_MEM_MALLOC_HOOKS=no and UCX_MEM_MALLOC_RELOC=no unless the user set them, so UCM can never swap allocators underneath us. Never set UCX_MEM_EVENTS=no: it turns off the rcache and the memory-type cache.
  • Deferred performance item. NextHeap unmaps every freed block of 256 KiB or more. MPI loops that allocate and free large buffers will re-register each time, which is the cost UCM's ptmalloc and glibc avoid by keeping freed memory mapped. A cache of retained blocks would fix it; I'd measure with OSU benchmarks first.

The existing rcache test sends from a buffer the application mmaps itself, so it never covers a freed malloc buffer reused at the same address. The verification plan adds that phase, plus a unit test of the private/release split that CI can run without UCX.

The scratch patch is in ucx-ucm-experiment.diff; the throwaway worktree has been removed. I didn't touch the uncommitted NextHeap retirement changes already in the working tree. Once you confirm the decisions, I can implement it.
